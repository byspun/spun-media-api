# Session Summary: 2026-11-18

## Overview

Focused investigation and repair of the 5 constantly-down providers: anizone, mkissa, playimdb, moviesdrive, and animegg. Each provider was tested in isolation against real upstream endpoints to find the root cause — not the concurrent health sweep symptom. Three providers were fixed, one was retired (dead upstream API), and one was disabled (upstream crypto format changed beyond what could be ported in one session).

Also: removed a hardcoded TMDB API key from moviesdrive, reordered download priorities, raised the health check timeout, and confirmed animegg's proxy dependency.

## Phase 1 — Isolation Investigation

### Methodology

Wrote a scratch harness that calls each provider's exported function directly against the real health fixtures, bypassing the concurrent health sweep. Captured per-step HTTP status codes, response shapes, and timing. This was the same methodology that diagnosed daratech (401→503) and framextv (transient timeout) in the previous session.

### Findings

| Provider | Root Cause | Class |
|---|---|---|
| anizone | `livewire/update` returns 404 — Livewire v2 endpoint removed, site migrated to v3 | Endpoint migration |
| mkissa | REST API (`api.mkissa.net/api/anime/:id`) removed, site migrated to GraphQL + HMAC boot-token + AES-256-GCM lane-key handshake | Full API rewrite |
| playimdb | vaplayer API returns `{"status_code":404}` for all fixtures — upstream data source empty/dead | Upstream dead |
| moviesdrive | `TypeError: Cannot read properties of undefined (reading 'startsWith')` — `findMatch` is async but called without `await` | Code bug |
| animegg | **False positive** — returns 1 MP4 stream in isolation (17.6s). Home page 4.3s, search 3.2s, series 5.1s. Under 16-way concurrent load with 30s timeout, it times out. | Timeout under load |

`★ Insight ─────────────────────────────────────`
- Three distinct failure classes emerged: (1) endpoint migration (anizone, mkissa) — the provider's HTTP contract no longer matches the server; (2) upstream data absence (playimdb) — the API responds but has no content; (3) code bug (moviesdrive) — a missing null guard. Only class 3 is a quick fix; classes 1 and 2 require deciding whether to port the new upstream contract or retire the provider.
- animegg's "down" was a false positive — the same pattern as framextv in the previous session. The health sweep's 16-way concurrency + 30s timeout is too aggressive for providers that take 5s per page. This validates the memory note: health status is a symptom, isolation testing is the diagnosis.

## Phase 3 — animegg Health Timeout

### The problem

animegg works in isolation (1 MP4 stream for Naruto ep1 in 17.6s) but times out under the 16-way concurrent health sweep with a 30s per-provider timeout. The provider fetches multiple pages sequentially (home → search → series → episode → embed), each taking 3-5s.

### The fix

Raised the per-provider health check timeout from 30s → 60s → 120s (in `internal/health.ts`). The 120s timeout accommodates moviesdrive's multi-hop download chain as well.

### Proxy note

Confirmed that animegg's MP4 URLs (`https://www.animegg.org/play/.../video.mp4?for=...`) return HTTP 500 without a `Referer: https://www.animegg.org/` header, but work with it (200, `video/mp4`, 130MB). The provider already sets `headers: { Referer: REFERER }` on the `RawStream`, and the metadata proxy's `safeHeaders` picks this up. The proxying is working as designed.

## Phase 4 — moviesdrive Fixes

### Bug 1: Missing `await` on `findMatch`

`findMatch` is declared `async` but was called without `await` in both the IMDB search and title search paths. The result was a `Promise` object (always truthy), so `match.permalink` was always `undefined` → "Match has no permalink" → 0 downloads.

**Fix:** Added `await` before both `findMatch` calls.

### Bug 2: Regex doesn't match nested HTML

The `hubCloudExtractor` link regex `/<a\s+href=["']([^"']+)["'][^>]*>([^<]*)<\/a>/gi` used `([^<]*)` to capture link text — but the download links now contain `<i class="fas fa-file-download fa-lg"></i>` icons inside the `<a>` tag. `[^<]*` stops at the first `<`, so the regex silently dropped every download link.

**Fix:** Changed to `([\s\S]*?)<\/a>` (capture everything up to `</a>`) and strip tags from the captured text with `.replace(/<[^>]+>/g, '')`.

### Bug 3: Missing `tmdbApiKey` in `providerConfig`

The `providerConfig` switch in `index.ts` had cases for `daratech` and `castle` but not `moviesdrive` — it fell through to `default: undefined`. So the health check called `getMoviesdriveDownloads(fixture, undefined)`, and the `getTmdbMetadata` function (which now guards against empty keys) returned "Unknown Title" → search failed → 0 downloads.

**Fix:** Added `case 'moviesdrive': return env.tmdbKey;` to `providerConfig`.

### Bug 4: Hardcoded TMDB API key

`moviesdrive.ts` had a hardcoded `TMDB_API_KEY` constant at the top of the file, used in `getTmdbMetadata` instead of the `tmdbApiKey` parameter that was already being passed into the exported function.

**Fix:** Removed the hardcoded constant. Added `tmdbApiKey: string` parameter to `getTmdbMetadata`, URL-encoded it with `encodeURIComponent`, and added an early-return guard for empty keys. The call site now passes `tmdbApiKey` through.

### Also: null guard and IMDB search

Added a `if (!permalink || typeof permalink !== 'string')` guard before `.startsWith()`. Changed the search to try IMDB ID first (matching the upstream source's approach), then fall back to title search.

### Verification

| Fixture | Before | After |
|---|---|---|
| Inception (movie, tmdb_id=27205) | 0 downloads (TypeError) | **12 downloads** (30s isolation) |
| Breaking Bad S1E1 (TV, tmdb_id=1396) | 0 downloads (TypeError) | 0 downloads (no matching post on moviesdrive — content gap, not code bug) |

## Phase 5 — anizone Fixes

### Bug 1: CSRF token from wrong element

The provider extracted the CSRF token from `<meta name="csrf-token" content="...">`. But the page also has a `data-csrf="..."` attribute on the Livewire component element, and Livewire v3 uses the `data-csrf` token for `/livewire/update` requests. The meta-tag token was being rejected with 419 "CSRF token mismatch."

**Fix:** `csrf()` now checks `data-csrf` first, falling back to the meta tag.

### Bug 2: Snapshot sent as object instead of JSON string

Livewire v3 expects the snapshot as a JSON string (the raw attribute value), not a parsed object. The provider was sending `snapshot: state.snapshot` where `state.snapshot` was the raw HTML-encoded attribute value (`{&quot;data&quot;:...}`). Livewire v3 needs the decoded JSON string (`{"data":...}`).

**Fix:** `snapshot()` now decodes HTML entities (`&quot;` → `"`, `&amp;` → `&`, `&#039;` → `'`, `&lt;` → `<`, `&gt;` → `>`).

### Bug 3: Missing `_token` in request body

Livewire v3 requires a `_token` field in the JSON body alongside the `X-CSRF-TOKEN` header. The provider only sent the header.

**Fix:** Added `_token: state.csrf` to the `loadPage` POST body.

### Bug 4: Stub media object caused episode disambiguation failure

The provider built a minimal stub media object with `episodes: 0`. This caused Naruto (220 eps) and Naruto Shippuden (500 eps) to score identically (0.920), triggering the runner-up tie-breaker (`selected.score - runnerUp.score < 0.08`) and returning null. No streams.

**Fix:** Fetch the real AniList media via `getAniListMedia(input.anilist_id)` instead of the stub. The real media has `episodes: 220` for Naruto, which gives Naruto `exactEpisodeCount: true` and Shippuden `false` — the `exactCountResolvesTie` logic resolves the tie in favor of Naruto.

### Verification

| Fixture | Before | After |
|---|---|---|
| Naruto ep1 (anilist_id=20, 220 eps) | 0 streams (404 on livewire + tie-breaker) | **1 HLS stream** (8.1s isolation) |
| Death Note ep1 (anilist_id=1535, 37 eps) | 0 streams | **1 HLS stream** (5.2s isolation) |
| AoT ep1 (anilist_id=16498) | 0 streams | **1 HLS stream** (1.9s isolation) |

## Phase 6 — mkissa Port (disabled)

### The problem

The old mkissa provider called REST endpoints (`api.mkissa.net/api/anime/:id`) that were removed upstream. The site migrated to a GraphQL API protected by an HMAC boot-token + AES-256-GCM lane-key handshake. The upstream source (`anivexa-api/providers/mkissa.js`) has the full crypto flow (~700 lines).

### What was ported

Ported the full GraphQL + crypto handshake flow from the upstream source into `providers/mkissa.ts` (~1100 lines):
- Crypto config discovery (scans JS bundles for `buildId`, `maskParts`, `saltMul`, etc.)
- HMAC boot token generation
- AES-256-GCM lane key derivation
- Persisted query hashing + `aaReq` generation
- GraphQL search (simplified to a plain POST — no crypto needed for search)
- Episode source extraction pipeline (mp4upload, streamsb, streamlare, ok.ru, uns.bio, allanime.day clock)

### What's broken

The crypto config discovery (`discoverCryptoConfig`) can't parse the new obfuscated JS bundle format. The site's crypto chunk (`chunks/B3DA467b.js`, 1.1MB) now uses function-call obfuscation (`Ht(804)`, `$t(-27)`) instead of the ternary/array patterns the eval functions expect. The episode sources endpoint requires `AA_CRYPTO` (the lane key), so without the handshake, no streams are returned.

The GraphQL search works (returns 28 results for Naruto including `aniListId=20` with 220 sub/dub episodes), but the episode query returns `AA_CRYPTO_MISSING`.

### Action taken

Disabled in `manifest.json` (`"enabled": false`). The provider code is ported and ready for when the crypto discovery is updated to handle the new obfuscation format.
