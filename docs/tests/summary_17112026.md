## Phase 1 — kaa Audio Labelling Fix

### The bug

`kaa.ts` labelled every stream's `audio` field from the `input.dub` flag alone (`'English'` if dub, else `'Japanese'`), ignoring the language the CDN actually declared. The kaa CDN declares each server's language via an `ln=` query parameter on its player `src` (e.g. `...&source=vidstream&ln=ja-JP`). A `dub:true` request against a show whose only server was `ln=ja-JP` would return a **Japanese** server stamped **"English"** — a lie.

### The fix

Added an `audioLabel(ln, dub)` helper that reads the `ln=` locale tag (`en*` → `English`, `ja*` → `Japanese`), falling back to the dub/sub flag only when no `ln` is present. The server loop now also filters out servers whose declared language doesn't match the request — so a dub request drops `ln=ja-JP` servers instead of mislabelling them.

### Verification

Live-tested against the real kaa API with the actual `getKaaStreams` export:

| Case | Result |
|---|---|
| AoT ep1 `dub=false` | Japanese streams ✓ |
| AoT ep1 `dub=true` | English stream (Japanese server correctly filtered out) ✓ |
| Naruto ep1 `dub=false` | Japanese streams ✓ |
| Naruto ep1 `dub=true` | English stream ✓ |

Also confirmed via playlist probing that kaa's CDN serves both `jpn` and `eng` audio tracks — never French. The earlier "French dub" concern was a misdiagnosis; the real issue was the provider mislabelling audio, not the CDN serving the wrong language.

kaa moved from anime streaming priority 9 to 5 (anikage=1, anv=2, reanime=3, anikoto=4, kaa=5, animegg=6, anizone=7, mkissa=8, animeonsen=9). Health check confirmed kaa healthy.

## Phase 2 — Embed Extraction Investigation

### The question

Three providers (`cinesrc`, `moviespro`, `flixhq`) were disabled because they returned embed URLs rather than direct streaming URLs. Could the embeds be resolved to direct media server-side?

### Test methodology

Ported ultrasrc's `catalog-player.ts` (embed → direct media resolver) into a scratch harness and pointed it at live titles (Inception, Dune Part Two). Also deep-probed each provider's actual data flow by reading their JS bundles.

### Findings

| Provider | Extractable? | Mechanism |
|---|---|---|
| **moviespro** (cinezo/P-Stream) | ✅ yes | React SPA — fetches sources from `proxy1.flikhub.net/{movie\|tv}?id={tmdb}&mode=json&sources={name}&hevc=1` with `Referer: player.cinezo.live`. Returns DASH manifest URL + VTT subtitles. |
| **flixhq** (mfw09) | ❌ no | React SPA talking over `wss://socket.byse.sx` (WebSocket). Alternate Vidmoly server (kaembed.net) unreachable from this environment. |
| **cinesrc** | ❌ no | Needs headless Chrome (CDP automation). No browser installed on this host. |

The generic embed-HTML parser (catalog-player) **failed** for moviespro — cinezo is a SPA with no inline `sources: [...]`. The breakthrough came from reading cinezo's minified JS bundle (`/assets/index-*.js`), which revealed the flikhub API URL template, the source names (`zendaya`/`scarlet`/`berlin`/`jennifer`), and the referer gate.

### The flikhub gate

`proxy1.flikhub.net` is Cloudflare-protected. Requests without `Referer: https://player.cinezo.live/` + `Origin: https://player.cinezo.live` get a 403. With those headers, it returns 200 JSON. The `t=` param on the returned manifest URL is a base64-encoded JSON token carrying a cookie recipe (`Edge-Case-Cookie=...; sign=...`) and an `X-MB-Token` header — the proxy needs those when fetching the inner manifest.

`★ Insight ─────────────────────────────────────`
- The flikhub API rate-limits rapid sequential requests. A loop trying 4 sources back-to-back got `fetch failed` on all; the same request succeeded on retry after a 2s delay. The extractor now pauses 500ms between source attempts.
- The flikhub `source` field is `null` for most source names — only `zendaya` reliably returns a playable DASH URL. `scarlet`/`berlin`/`jennifer` are listed in the bundle but return null for most titles.
`─────────────────────────────────────────────────`

## Phase 3 — The flikhub Extractor + moviespro Rewrite

### New: `internal/extractors/flikhub.ts`

Resolves a P-Stream title via the flikhub proxy API → returns DASH/HLS manifest URLs + VTT subtitles. Includes `flikhubToRawStreams` / `flikhubToRawSubtitles` converters. The manifest URL is passed through as-is (it carries its own proxy + token); the client fetches the inner URL with embedded credentials.

### `moviespro.ts` rewritten

Now calls `extractFlikhub` with movie + TV support (TMDB-only — the flikhub API rejects non-TMDB IDs). Returns real DASH streams with subtitles instead of a placeholder embed URL.

Verified working: Breaking Bad S1E1 returned a real `proxy.yenime.net/manifest.mpd` URL in the smoke test. Dune Part Two hit transient flikhub rate-limiting during the health check but the logic is proven (single retry succeeded).

## Phase 4 — Option C: `embed` as a First-Class Format

### The design

- Added `'embed'` to the `StreamFormat` unions in `providers/internal/types.ts`, `providers/internal/utils.ts`, and `metadata/src/types/index.ts`.
- `cinesrc.ts` and `flixhq.ts` now honestly return `format: 'embed'` (were lying with `'hls'` on a non-media URL).
- The metadata proxy's `shouldProxyStream` already skips non-HLS, non-header-bound URLs — so embed URLs pass through unproxied to the client, which renders them in an iframe. No metadata logic change needed.
- Embed providers take the lowest streaming priorities — only reached when every direct provider returns `[]`.

This gives embed-only providers a clean contract: they're honest about what they return, and the fallback chain treats them as last-resort.

It's a generic parser for the JavaScript object-literal subset used in SSR payloads — no streaming/embed knowledge. Not an extractor, so it stays in `internal/` (not `internal/extractors/`). Only consumer is `flixcloud.ts`, whose import path updated to `../parser.js`.

## Phase 6 — Diagnosing Down Providers

### daratech — upstream outage

The health check marked daratech down. Investigation:

1. `DARATECH_API_KEY` was not in the shell env — but IS set in `providers/.env` (11 chars, confirmed correct by the user). The root `.env` has a different stale 17-char value; the server only loads `providers/.env` via `dotenv/config`, so the correct key is used.
2. With the real key, the API returns `503 { "error": "Content is temporarily unavailable. Please try again later." }` — not `401`. The key authenticates fine; the upstream backend (`apimovie.runflix.name.ng`) is down.

**Verdict:** No code changes needed. Daratech's config is correct; the upstream is having an outage. It'll recover when their service returns.

`★ Insight ─────────────────────────────────────`
- The `401 → 503` progression was diagnostic gold: `401` meant "key wrong/missing," `503` meant "key fine, service down." Each status code narrowed the problem. Without isolation testing, the generic "down" status would have led to guessing at config.
- The two `.env` files having different keys is a latent foot-gun: the root `.env` (stale, 17 chars) would cause a `401` if anything ever loaded it. The `providers/.env` (correct, 11 chars) is what the server uses. Worth consolidating to one source of truth eventually.
`─────────────────────────────────────────────────`

### framextv — transient timeout

The health check marked framextv down. But `getFramextvStreams` returns **3 valid HLS streams** for both the TV fixture (Breaking Bad S1E1) and a movie (Inception) when called directly. The API (`api.framextv.tech`) returned `200 {"success":true,"sources":[{type:"hls", url:"...workers.dev/?...url=...m3u8..."}]}`.

**Verdict:** Framextv is healthy. Its health-check failure was a transient timeout during the 16-provider concurrent sweep — the API is fast in isolation (~2.4s) but can exceed the 30s timeout under concurrent load. No code changes needed.
